# CQM 명령문 생성기 설계 근거와 확장 아이디어

## 다차원 분석과 문제 재정의의 결합

이 프로젝트에는 다차원 분석(MDA)과 문제 재정의(PR)를 적용했다. 수식은 측정 가능한 과학적 성과 지표가 아니라 제품 설계를 정리하는 관점으로 사용한다. 핵심 과제는 Markdown을 예쁘게 보여주는 것이 아니라, 사람이 매번 바꾸는 작업 정보와 반복해서 전달해야 하는 제작 기준을 안정적으로 결합하는 것이다. 따라서 화면의 성공 기준은 긴 문서를 짧게 만드는 정도보다, 입력 누락과 과거 상품값의 재사용을 줄이면서 다른 AI 도구에 전달할 수 있는 요청을 만드는 데 둔다.

시간 차원에서는 세 가지 정보의 수명이 다르다. 상품명과 Figma 노드 링크는 작업마다 바뀌고, 제작 가이드는 상대적으로 오래 유지되며, 과거 상품의 수정 지시는 특정 시점에만 유효하다. 이 셋을 하나의 문자열에서 직접 편집하면 이전 상품의 RMS 번호나 수정 범위가 다음 작업에 남을 수 있다. 실제 첨부 문서에도 여러 상품명과 이미지 폴더번호가 함께 등장한다. 따라서 현재 입력은 구조화된 상태로, 반복 지침은 정적 문서로, 과거 예시는 참고 정보로 구분했다. 현재 입력을 원문 예시로 자동 보충하지 않는 것은 이 시간적 차이를 반영한 결정이다.

공간 차원에서는 앱의 프로젝트 폴더와 명령문을 받을 AI의 작업 폴더를 구분해야 한다. React 앱이 실행되는 commands 폴더는 인터페이스의 소스 위치이고, VAR-00은 나중에 제작 AI가 사용할 콘텐츠 작업공간 안의 상대경로다. 두 경로를 같은 대상으로 해석하면 앱 프로젝트에 상품 HTML을 생성하거나 사용자가 기대하지 않은 폴더를 수정할 수 있다. 따라서 앱은 경로 문자열과 예상 파일 목록만 만들며, 실제 파일 제작은 전달받은 AI가 수행한다고 화면과 README에 명시했다. Figma 링크 역시 앱이 원격 디자인을 읽는 기능과 요청에 링크를 포함하는 기능을 구분한다.

계층 차원에서는 상품, 출력 섹션, 기기, 상태 그룹, 상태 항목이라는 구조가 중요하다. 상품은 여러 섹션을 포함하고 각 섹션은 PC와 MO의 독립적인 디자인을 가진다. 각 기기에는 탭이나 아코디언 그룹이 여러 개 존재할 수 있으며, 각 그룹은 여러 상태 프레임을 참조한다. 상태 항목이 늘어나는 것이 출력 파일 증가를 뜻하지 않는다. 이 관계를 데이터 모델에 직접 표현하면 탭마다 폴더를 생성하는 오류를 예방할 수 있다. 화면도 섹션 안에 기기 입력과 상태 그룹을 배치하여 사용자가 이 관계를 자연스럽게 이해하도록 설계했다.

인과 차원에서는 잘못된 결과를 만드는 원인을 생성 직전보다 입력 시점에 발견하는 편이 유용하다. node-id가 없는 링크, 같은 섹션 폴더명, 탭 구성인데 상태 그룹이 없는 입력, 펼친 상태 링크의 누락은 명령문 자체에서 확인할 수 있다. 반면 Figma 접근 권한, 실제 노드의 내용, 공통 배치의 충분성은 문자열 검사로 알 수 없다. 따라서 앱의 검사는 입력 일관성에 한정하고, 외부 디자인을 검증했다고 표현하지 않는다. 사용자는 오류 개수와 항목을 확인한 뒤 고칠 수 있으며, 생성 파일 미리보기로 작업 범위를 별도로 점검한다.

문제 재정의에서는 원래의 '전체 명령문 자동 생성'을 '매 작업의 확정값을 반복 지침과 결합해 전달하는 작은 편집기'로 구체화했다. 관점을 AI 제공자에서 작업자에게 옮기면 Codex와 Kiro의 세부 사용법보다 상품명, Figma 노드, 에셋 경로, 출력 범위를 정확히 전달하는 것이 우선이다. 이에 따라 대상 도구 선택은 요청의 수신 도구를 표시하는 역할만 하며, 서로 다른 기능이 실제로 연동된 것처럼 표현하지 않는다. 범위도 전체 CMS나 디자인 자동화 플랫폼으로 확대하지 않고 CQM 한 유형의 반복 입력을 먼저 해결한다.

실행 결과물의 검증과 명령문 생성 앱의 검증도 서로 다른 범위다. 원본의 '별도 검증은 요청 시 수행'이라는 문구는 앞으로 생성할 콘텐츠 제작 지시다. 그것을 React 앱의 빌드나 입력 로직 검사 금지로 해석하면 오히려 도구의 신뢰성이 낮아진다. 이번 앱은 필수값과 파일 계산 규칙을 테스트하고 빌드하되, Figma 기반 상품 HTML의 제작·검증을 수행했다고 주장하지 않는다. 두 범위의 구분은 원본 문서를 데이터로 다루면서 현재 사용자 요청을 완수하기 위한 기준이다.

기본 UI는 네 단계와 실시간 미리보기로 정했다. 기본 정보는 작업의 정체성, Figma 디자인은 출력 범위, 에셋·버튼은 연결 정보, 생성 설정은 전달 방식에 해당한다. 사용자는 단계 사이를 자유롭게 이동하고 입력값을 브라우저에 보관할 수 있다. 전체 가이드를 포함하면 명령문 길이는 늘어나지만 다른 작업공간에서 참조 파일이 누락되는 문제를 줄인다. 이미 문서를 갖춘 환경에서는 전문 포함을 끌 수 있다. 이 선택은 정보의 완전성과 전달 길이 사이의 실질적인 절충을 사용자에게 제공한다.

## 확장 아이디어 12개

아래는 향후 검토할 제안이다. 현재 구현 완료 기능과 구분하며 자동으로 추가하지 않았다.

1. **콘텐츠 유형별 입력 계약**
   CQM 다음으로 블로그·고객사례·뉴스레터를 추가할 때 하나의 거대한 조건문으로 통합하지 않고, 유형마다 입력 스키마와 생성 함수를 가진 템플릿을 등록한다. 공통 상품명이나 링크는 재사용하되 유형 고유의 출력 형식과 필수값을 유지한다. 이를 통해 CQM의 섹션 폴더 규칙이 뉴스레터의 기존 파일 수정 작업에 섞이는 문제를 줄일 수 있다. 첫 실험은 두 번째 유형을 추가할 때 기존 CQM 테스트를 변경하지 않고 통과시키는 것이다. 유형 전환 시 이전 입력을 어느 범위까지 유지할지도 명시적으로 설계한다.

2. **원본 문서 변경 비교와 버전 고정**
   제작 가이드가 수정되면 바뀐 문장을 보여주고 기존 프로젝트가 어느 문서 버전에 연결되었는지 기록한다. 단순히 최신 전문으로 교체하면 이전 작업을 재현하기 어렵기 때문에 작업 JSON에 문서 버전과 해시를 저장하는 방법을 검토한다. 사용자는 새 규칙으로 전환하거나 기존 기준을 유지할 수 있다. 초기 구현은 가이드 변경 전후의 제목과 문단 차이를 보여주는 수준으로 시작할 수 있다. 효과는 담당자가 기억에 의존하지 않고 생성 결과의 기준을 추적할 수 있다는 데 있다.

3. **확정값과 미확정값의 분리**
   비어 있는 필드가 의도적인 미적용인지 아직 확인하지 못한 값인지 구분한다. 예를 들어 MO 디자인이 없는 상품과 모바일 링크를 아직 받지 못한 상품은 같은 빈 문자열이어도 의미가 다르다. 각 기기를 '제작', '해당 없음', '확인 중' 상태로 표시하면 실행 범위를 더 정확히 전달할 수 있다. 기본 입력 부담을 늘리지 않도록 필요한 항목만 확장하는 방식이 적합하다. 확정 상태는 명령문에 명시하고 확인 중인 항목은 완료된 것으로 계산하지 않는다.

4. **작업별 명령문 변경 비교**
   이전에 복사한 요청과 현재 요청을 비교하여 상품명, 출력 범위, 디자인 링크, 에셋 번호의 변화를 강조한다. 긴 가이드 전문 전체를 다시 검토하기보다 변경된 입력과 영향받는 파일을 먼저 보여주는 기능이다. 특히 후속 수정에서 어느 섹션이 바뀌었는지 알기 쉬워진다. 처음에는 마지막 복사 시점의 구조화된 입력만 저장하고 필드 단위 비교를 제공하면 된다. 이 기능은 AI가 실행한 결과를 추적하는 기능과 구분하여 '요청의 차이'만 보여줘야 한다.

5. **Figma 노드 중복 사용 안내**
   여러 항목이 같은 노드를 참조하는 경우 즉시 오류로 막기보다 사용 위치를 모아 보여준다. 아코디언의 접힌 전체 화면은 여러 항목에서 같은 프레임을 공유할 수 있기 때문이다. 사용자는 정상적인 공통 프레임 재사용인지 실수로 같은 링크를 붙였는지 판단한다. 앱은 '같은 링크가 세 곳에서 사용됨'처럼 관찰 가능한 사실만 안내하고 디자인 내용을 추정하지 않는다. 이 접근은 잘못된 자동 차단을 줄이면서 대량 링크 입력의 실수를 발견하는 데 도움이 된다.

6. **작업공간용 가이드 묶음 내보내기**
   긴 전문을 매번 복사하는 대신 정규화된 파일명으로 가이드 파일과 짧은 실행 명령문을 함께 내려받는 기능을 검토한다. 원본 파일명이 괄호나 숫자 접미사를 포함해도 명령문이 기대하는 이름과 대응하도록 묶음에 명세를 넣는다. 사용자는 대상 프로젝트에 묶음을 배치한 뒤 짧은 명령문을 전달할 수 있다. 원본 보존 파일과 실행 참조 파일의 차이를 설명하고 어떤 문서도 자동으로 외부 작업공간에 쓰지 않도록 설계한다. 전문 포함 모드와 함께 제공할 수 있다.

7. **실행 범위의 시각적 지도**
   섹션별로 PC와 MO의 생성 여부, 상태 그룹 수, 예상 파일 경로를 행과 열로 보여준다. 현재 파일 목록보다 프로젝트가 커졌을 때 전체 범위를 빠르게 파악할 수 있다. 예를 들어 PC 탭과 MO 아코디언의 차이를 같은 행에서 비교하면 모바일 상태 링크를 빠뜨린 부분을 찾기 쉽다. 여기서 상태 프레임 수와 출력 파일 수는 다른 지표로 표시한다. 최초 적용은 열 개 이상의 섹션이 있는 작업에서 요약 화면이 실제 검토 시간을 줄이는지 확인하는 실험이 적절하다.

8. **반복 버튼의 연결 프로필**
   같은 상담 버튼이 여러 영역에서 반복될 때 문구와 URL·동작의 공통 부분을 묶고, 영역별로 다른 연결만 따로 지정하도록 개선한다. 단, 상품 간 버튼 URL이나 GTM을 자동으로 이어받는 기능으로 확대하지 않는다. 저장된 프로필을 새 작업에 적용할 때는 적용값을 화면에 명확히 표시하고 사용자가 범위를 확인할 수 있어야 한다. 동일 문구라도 다른 목적지로 이동하는 버튼을 하나로 합치지 않는 것이 핵심이다. 초기에는 현재 작업 안의 명시적인 재사용 기능으로 제한한다.

9. **긴 명령문의 전달 길이 안내**
   현재 문자 수 외에 변수, 실행 지시, CQM 가이드, 공통규칙이 각각 차지하는 길이를 나누어 표시한다. 사용자는 전문 제외 시 어느 부분이 빠지는지 이해하고 대상 도구의 입력 상황에 맞게 선택할 수 있다. 토큰 수를 표시하려면 사용하는 토크나이저와 추정 조건을 함께 안내해야 하며, 문자 수를 정확한 토큰 수처럼 표현해서는 안 된다. 가이드 축약 기능을 추가하더라도 핵심 규칙이 사라지지 않았다는 확인 절차가 필요하다. 우선은 정확한 문자 수 분해만으로 시작할 수 있다.

10. **재개 가능한 여러 작업 초안**
    단일 자동 저장을 여러 프로젝트 초안 목록으로 확장하면 동시에 진행하는 상품 간 전환이 쉬워진다. 초안마다 상품명, 마지막 수정 시간, 선택 섹션 수, 입력 완료 상태를 표시한다. 새 작업을 만들 때 이전 상품값이 자동 복제되지 않도록 빈 초안 생성을 기본으로 두고, 복제는 명시적인 동작으로 제공한다. 브라우저 저장 용량과 백업 방식도 함께 고려해야 한다. 첫 단계는 로컬 목록과 JSON 백업을 유지하는 것으로 충분하며 로그인이나 서버 저장은 실제 협업 수요가 생긴 뒤 결정한다.

11. **문서의 충돌 후보 안내**
    공통규칙과 유형별 가이드에서 같은 주제의 상반된 문장이 발견되면 우선순위를 보여주는 참고 패널을 만든다. 예를 들어 공통 alt 길이 규칙과 CQM의 의미 중심 예외처럼 의도적인 차이가 있을 수 있으므로 자동 수정하거나 한쪽을 삭제하지 않는다. 문서 위치, 해당 문장, 적용 우선순위를 함께 보여주는 것이 목표다. 처음에는 수동으로 확인한 충돌 목록을 관리하고, 자동 탐지는 검토 후보를 제안하는 수준으로 제한한다. 현재 입력 범위를 과거 사례보다 우선하는 기준도 이 패널에 포함할 수 있다.

12. **제작 완료 결과의 최소 기록 연결**
    AI에 전달한 요청과 나중에 실제 생성된 파일 목록을 연결하여 요청 대비 완료 상태를 확인하는 기능을 검토한다. 다만 명령문을 복사했다는 사실만으로 제작 완료를 표시해서는 안 된다. 사용자가 완료 결과를 직접 붙여넣거나 허용된 연결 도구로 확인한 경우에만 실제 결과를 기록한다. 검증 수행 여부도 제작 완료와 별도 상태로 유지한다. 원본의 단일 작업내역 파일 원칙을 고려해 새로운 보고서를 무분별하게 늘리지 않고 기존 기록에 옮길 짧은 요약을 만드는 방식부터 실험할 수 있다.
